# project-handover 推广包

这是一套可直接改写成抖音/小红书图文、X/LinkedIn 帖子、知乎/V2EX 文章的素材包。包含第一性原理计划、主配文、平台改写、3 张直接生成中文成品的绘图提示词、发布检查和视频版分镜。

> 图片尚未生成。当前环境不能调用 DeepSeek-v4-Flash-Vision；请用 [`image-prompts.md`](image-prompts.md) 的提示词直接生成 3 张中文成品图，不需要后期叠字。

## 1. 第一性原理

不要从“我要更多 star”出发，而从“用户为什么会主动转发”出发。

1. 用户不是缺一个交接工具，而是缺一个不用重新解释项目的办法。
2. 聊天记录不是项目状态；真正可交接的是目标、决策、死路、证据和下一步。
3. 图文平台不消费功能列表，只消费“3 秒内能认出的问题”。
4. Star 是结果，不是动作。可执行的动作是：让目标用户完成一次成功交接。
5. 一次成功交接会产生两个传播点：省下的时间，以及“新 agent 直接说对了下一步”的瞬间。
6. 上下文成本有三层：token 重复计费、响应变慢、注意力被旧信息稀释。交接要同时解决这三层。

## 2. 核心信息

- 中文一句话：**交接项目，而不是交接聊天记录。**
- 英文一句话：**Hand over the project, not the chat.**
- 目标用户：用 Codex、Claude Code 或其他 agent 做多步项目的开发者、独立开发者、研究者和写作者。
- 核心痛点：长期项目上下文越积越厚；每次新对话重复喂上下文，token 成本持续上升；旧目标、废弃方案和过时结论稀释注意力，形成上下文污染。
- 承诺：不是只写硬约束，而是完整覆盖交接类目；按项目类型检查，发现信息缺口会主动追问。
- 证据：两份真实文件、只读安全检查、带证据的状态表、按任务类型追问缺口、可独立粘贴的接手提示词。
- 行动：`npx skills@latest add NormanGOING/project-handover`

## 3. 漏斗

| 阶段 | 用户问题 | 素材要做的唯一一件事 |
|---|---|---|
| 3 秒 | 这和我有关吗？ | 让“长期上下文越积越厚、token 重复燃烧”的痛感被立刻认出 |
| 10 秒 | 这到底是什么？ | 用“两份文件”把抽象概念变成具体物件 |
| 30 秒 | 它和聊天摘要有什么不同？ | 展示完整交接类目、决策、死路、证据和主动追问 |
| 1 分钟 | 我信吗？ | 用真实文件、git 状态和测试结果做证据 |
| 行动 | 怎么试？ | 给出唯一一条安装命令 |

## 4. 两周执行计划

### 第 1–2 天：把仓库本身变成可传播的落点

- 填 Topics，补 `v0.1.0` Release。
- 在 README 顶部放 30–60 秒演示 GIF。
- 加一个完整示例目录，让访客不安装也能看到成品。

### 第 3–5 天：先发中文图文

- 抖音/小红书：3 张 3:4 图文，使用本包主配文。
- 同一天在评论区置顶安装命令和 GitHub 链接。
- 记录保存、分享、评论和主页访问，不只看点赞。

### 第 6–8 天：开发者渠道

- 提交 2–3 个 awesome lists，先读各自的 `CONTRIBUTING.md`。
- 在 X/LinkedIn 发英文短帖，配 4 张图或一张总览图。
- 在知乎/V2EX 发技术版，不发营销版。

### 第 9–10 天：放大有效内容

- 如果某一张图的保存率明显高，把它做成视频封面或单独帖子。
- 如果安装量高但 star 低，优化 README 的“这是什么”和首屏 CTA。
- 如果访问高但安装低，优化安装步骤和首个示例。

### 第 11–14 天：沉淀

- 写一篇技术文章：为什么聊天摘要不能替代项目交接。
- 收集 2–3 条真实反馈，更新 README 的“适用场景”。
- 复盘一次，不追加新平台，先把一个渠道做透。

## 5. 衡量

只看四个数：

1. **GitHub 访问 → star 转化率**：Insights → Traffic，判断首屏是否清楚。
2. **skills.sh 安装量**：首次真实安装后页面才会出现。
3. **安装 → 首次成功交接**：用 issue/评论问“你生成出两份文件了吗”。
4. **分享/收藏/评论**：比点赞更能说明内容是否值得保存。

两周的合理目标不是“爆”，而是：20 次有效安装、10 个 star、3 条真实反馈。这个量级足以判断定位是否成立。

## 6. 平台适配

| 平台 | 形式 | 语气 | 注意 |
|---|---|---|---|
| 抖音 | 3 张竖屏图文，3:4 | 直接、强钩子、短句 | 第一张图必须独立成立；安装命令放评论置顶 |
| 小红书 | 同一组图 | 工具分享、经验感 | 标题带“AI 编程/上下文管理/Codex” |
| 知乎/V2EX | 长文，图辅助 | 技术、克制 | 先讲问题和设计，再放链接 |
| X/LinkedIn | 1 张总览图或 3 图 | 英文、简洁 | 用 thread 展开两份文件的设计 |
| GitHub | Release notes + README | 事实、可验证 | 不写营销形容词，写能做什么 |

## 7. 视频扩展

不需要一上来做 AI 视频。最容易跑通的形式是“录屏 + 3 张图文 + 配音”，30–45 秒：

| 时间 | 画面 | 旁白 |
|---|---|---|
| 0–3s | 图 1：成本、污染与两份文件 | 长期项目最贵的，不是写代码，是上下文越积越厚。 |
| 3–8s | 图 1 局部：聊天纸条和警示牌 | 每次新对话都在重复烧 token，旧结论还会污染判断。 |
| 8–15s | 图 2：完整交接类目 | 我把交接改成两份文件：一份写状态和证据，一份直接告诉新 agent 下一步。 |
| 15–25s | 录屏：让 agent 生成交接包 | 它会检查对话、文件、git 状态和测试结果，然后写出两份文件。 |
| 25–35s | 录屏：新对话粘贴接手提示词 | 新 agent 先复述目标、死路和第一步，再开始动手。 |
| 35–45s | 图 3：接手流程与安装命令 | 如果你也受够了从头解释，试试 project-handover。 |

## 8. 未来可以做成 skill

这个计划可以抽象成一个 `promo-carousel` skill：

- 输入：产品/仓库、目标用户、核心痛点、证据、目标平台。
- 输出：核心信息、3 页分镜、逐页文案、绘图提示词、平台改写、发布检查和指标表。
- 复用阶段：受众 → 承诺 → 证据 → 钩子 → 分镜 → 渠道改写 → 复盘。

先手动跑 2 次。如果每次都要重写同样的结构，再把它 skill 化；现在直接建 skill 容易把一次 campaign 的偏好固化成规则。
